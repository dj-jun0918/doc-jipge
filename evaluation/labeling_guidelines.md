## 2. 표준 7종 필드 정책 (PR#12 확정 + v0.3 유지)

`fields` 배열에는 **아래 7가지 `field_name`만** 사용한다.

| # | field_name | 설명 |
|---|-----------|------|
| 1 | `"업력"` | 창업 후 경과 연수 조건 |
| 2 | `"매출"` | 매출액(또는 매출) 조건 |
| 3 | `"지역"` | 소재지 조건 |
| 4 | `"나이"` | 대표자/신청자 연령 조건 |
| 5 | `"종업원 수"` | 임직원 수 조건 |
| 6 | `"업종"` | 허용/제외 업종 조건 |
| 7 | `"인증"` | 보유 인증 조건 |

### 비표준 자격요건 처리 원칙

| 케이스 | 처리 방법 |
|--------|-----------|
| 표준 7종과 의미가 같은 자격요건 | 표준 필드명으로 매핑. 예: `"스타트업 업력"` → `"업력"` |
| 표준 7종으로 매핑하기 어려운 자격요건 | `fields` 제외, `notes`에 원문과 매핑 불가 사유 기록. 예: `"대표자 국적"` |
| 메타 정보 (사업기간/신청방법/지원한도/제출서류 등) | **자격요건이 아니므로 `fields`에서 완전 제외** |
| 표준 7종 어디에도 매핑 안 되는 공고 | `fields: []` 허용 (§6 참고, ann_011 모범 사례) |

> ⚠️ `fields`는 오직 **"이 공고에 신청하려면 어떤 자격을 갖춰야 하는가"**에 대한 답만 담는다.
> 지원 내용, 사업 일정, 제출 서류, 지원 금액 등은 메타 정보이므로 절대 포함하지 않는다.

## 3. 핵심 원칙 (v0.3 신규)

GT의 `condition`은 사용자 표시용 텍스트지만, **시스템과 비교하려면 `value` + `operator`를 함께 명시해야 한다.** 시스템 `ParsedCondition`과 동일 구조.

```python
# backend/app/schemas/eligibility.py:7-11
class ParsedCondition(BaseModel):
    value: float | str | dict | None
    operator: str | None
    raw_text: str
```

### value 형식 요약

| 필드 | value 형식 | 예시 |
|---|---|---|
| 업력 | int 또는 float (년) | `7` |
| 매출 | int (원) | `200000000` (= 2억원) |
| 나이 | int (만 나이) | `39` |
| 종업원 수 | int (명) | `5` |
| 지역 | string 배열 | `["원주"]`, `["강원", "서울"]` |
| 업종 | string 배열 | `["제조업"]`, `["IT", "SW"]` |
| 인증 | string 또는 string 배열 | `"venture_company"`, `["venture_company", "iso_9001"]` |
| 범위 | `{"min": N, "max": M}` | `{"min": 1, "max": 50}` |

### operator 11종

`"미만"` | `"이하"` | `"이상"` | `"초과"` | `"범위"` | `"소재"` | `"무관"` | `"포함"` | `"제외"` | `"보유"` | `"미보유"`

## 4. 필드별 라벨링 기준 (v0.3 — value/operator 통합)

### 4-1. 업력

- `field_name`: `"업력"`
- `condition`: 사용자 표시용 텍스트 — `"3년 미만"`, `"7년 이하"`, `"6개월 이상"`, `"창업 후 7년 이내"`
- `value`: 년 단위 int 또는 float
- `operator`: `"미만"` | `"이하"` | `"이상"` | `"초과"` | `"범위"`
- `evidence`: 조건이 명시된 원문 문장 그대로 인용
- `evidence_source`: 페이지 + 항목 위치

**operator 매핑 기준**

| 원문 표현 | operator |
|-----------|----------|
| N년 미만 | `"미만"` |
| N년 이하 | `"이하"` |
| N년 이상 | `"이상"` |
| N년 초과 | `"초과"` |
| N년 이상 M년 이하/미만 | `"범위"` |

> ⚠️ `"미만"`과 `"이하"` 엄격 구분. `"창업 후 3년"` 표현은 문맥상 `"이하"` 또는 `"미만"` 판단하여 `notes`에 근거 기재.
> ⚠️ `condition`은 사용자에게 보여지는 값이므로 `"창업 후 7년 이내인 기업"`처럼 긴 문장보다 `"창업 후 7년 이내"`처럼 조건 중심 표현 권장.

**예시**:
```json
{
  "field_name": "업력",
  "condition": "7년 이하",
  "value": 7,
  "operator": "이하",
  "evidence": "창업 7년 이내 중소기업",
  "evidence_source": "첨부파일 2p 2. 지원대상"
}
```

```json
{
  "field_name": "업력",
  "condition": "1년 이상 7년 이하",
  "value": {"min": 1, "max": 7},
  "operator": "범위",
  "evidence": "창업 1~7년차 기업",
  "evidence_source": "본문 1p"
}
```

### 4-2. 매출

- `field_name`: `"매출"` (원문이 `"매출액"`이어도 **항상 `"매출"`으로 통일** — measure.py `STANDARD_FIELDS`가 `"매출"`만 인식하므로 `"매출액"`은 비표준으로 필터됨)
- `condition`: 사용자 입장에서 기준이 분명한 텍스트
  - 예: `"2억원 이상"`, `"10억원 미만"`, `"1억원 이상 50억원 미만"`
  - 기준 연도/기간이 명시된 경우 그대로 포함:
    `"직전년도(2025) 또는 최근 3개년 연매출 2억원 이상"`
- `value`: **원 단위 정수** (시스템 `Company.revenue: BigInteger` 정렬) — 부록 3 참고
- `operator`: `"미만"` | `"이하"` | `"이상"` | `"초과"` | `"범위"`

**사용자 표시 관점 보완**
- `"2억원 이하"`처럼 금액만 있으면 사용자가 기준 시점을 오해할 수 있으므로, 원문에 기준 연도나 기간이 있으면 반드시 포함
- 화면에 표시될 값임을 고려해 `"직전년도 매출 2억원 이하"`처럼 읽히는 형태 권장

**예시**:
```json
{
  "field_name": "매출",
  "condition": "2억원 이상",
  "value": 200000000,
  "operator": "이상",
  "evidence": "직전년도 매출액 2억원 이상",
  "evidence_source": "첨부파일 3p ③(매출액)"
}
```

```json
{
  "field_name": "매출",
  "condition": "1억원 이상 50억원 미만",
  "value": {"min": 100000000, "max": 4999999999},
  "operator": "범위",
  "evidence": "1억원 이상 50억원 미만",
  "evidence_source": "본문 2p",
  "notes": "원문 '50억원 미만'을 inclusive로 변환 (max: 4999999999)"
}
```

### 4-3. 지역

- `field_name`: `"지역"`
- `condition`: 사용자 입장에서 의미가 명확한 텍스트 — `"원주시 소재"`, `"강원 소재"`, `"전국"`
- `value`: **string 배열** (광역시·도 또는 시·군·구 단위)
  - 광역시·도는 `REGION_GROUPS` 기준 정규화 (`강원특별자치도` → `"강원"`)
  - 시·군·구는 원문 그대로
  - 전국 조건은 `value: null`
- `operator`: `"소재"` (특정 지역) | `"무관"` (전국)

**전국 조건 처리**
- `"전국 소재"`, `"제한 없음"`, `"지역 무관"` → `condition: "전국"`, `value: null`, `operator: "무관"`
- 시스템 matcher는 `raw_text`에 `"전국"` 포함 시 항상 충족 처리

**사용자 표시 관점 보완**
- `condition`은 `"강원 소재"`, `"서울 소재"`처럼 `"소재"` 어휘 포함 권장 (단순 지역명만 쓰면 의미 모호)
- 시·군·구는 원문 그대로 유지하되, 사용자가 거주지 기준인지 사업장 기준인지 오해할 수 있는 경우 `notes`에 명시

**예시**:
```json
{ "field_name": "지역", "condition": "원주시 소재", "value": ["원주시"], "operator": "소재" }
{ "field_name": "지역", "condition": "강원 소재", "value": ["강원"], "operator": "소재" }
{ "field_name": "지역", "condition": "강원 또는 서울 소재", "value": ["강원", "서울"], "operator": "소재" }
{ "field_name": "지역", "condition": "전국", "value": null, "operator": "무관" }
```

> 💡 시·군·구는 원문 그대로 (`"원주시"`), 광역시·도는 정규화 (`"강원"`). 이렇게 분리하면 광역시·도(`["강원"]`)와 시·군·구(`["원주시"]`)가 명확히 구분됨.

### 4-4. 종업원 수

- `field_name`: `"종업원 수"`
- `condition`: 원문 그대로
  - 예: `"5인 미만"`, `"10인 이상 300인 미만"`
  - 업종별 기준 상이: `"광업·제조·건설·운수업 10인 미만 / 그 외 업종 5인 미만"`
- `value`: 정수 또는 `{"min": N, "max": M}` (업종별 복합 조건은 `notes`에 분기 명시 + 대표값만 value로)
- `operator`: `"미만"` | `"이하"` | `"이상"` | `"초과"` | `"범위"`

**예시**:
```json
{
  "field_name": "종업원 수",
  "condition": "10인 이상 300인 미만",
  "value": {"min": 10, "max": 299},
  "operator": "범위",
  "notes": "원문 '300인 미만'을 inclusive로 변환 (max: 299)"
}
```

### 4-5. 나이

- `field_name`: `"나이"`
- `condition`: 만 나이 명시 — `"만 39세 이하"`, `"만 60세 이상"`
- `value`: 만 나이 정수
- `operator`: `"미만"` | `"이하"` | `"이상"` | `"초과"` | `"범위"`
- `"만 나이"` 표현 필수 확인 — `"만"` 없는 경우 `notes`에 명기

**사용자 표시 관점 보완**
- 대표자 기준인지 신청자 기준인지 불명확하면 `notes`에 근거 기재

**예시**:
```json
{
  "field_name": "나이",
  "condition": "만 39세 이하",
  "value": 39,
  "operator": "이하",
  "evidence": "대표자 만 39세 이하인 청년 창업기업",
  "evidence_source": "본문 1p"
}
```

### 4-6. 업종

- `field_name`: `"업종"`
- `condition`: 허용/제외 업종 원문 — 예: `"제조업"`, `"소상공인 정책자금 지원제외 업종 외"`
- `value`: **string 배열** (업종명, 키워드, 또는 KSIC 명)
- `operator`: `"포함"` (허용) | `"제외"` (금지)
- 업종 목록 매우 긴 경우: 대표 3~5개 + 나머지는 `notes`에 출처 기재

**사용자 표시 관점 보완**
- 업종은 공고 원문이 법률 문장처럼 길어질 수 있으므로, 사용자 입장에서 읽히는 수준으로 정리
- 의미를 바꾸지 않는 범위에서만 요약

**예시**:
```json
{
  "field_name": "업종",
  "condition": "제조업",
  "value": ["제조업"],
  "operator": "포함",
  "evidence": "제조업 영위 기업",
  "evidence_source": "본문 1p"
}
```

```json
{
  "field_name": "업종",
  "condition": "소상공인 정책자금 지원제외 업종 외",
  "value": ["유흥주점", "도박업", "사행성"],
  "operator": "제외",
  "notes": "전체 목록: 중소기업창업 지원법 시행령 제4조 (대표 3개만 명시)"
}
```

### 4-7. 인증

- `field_name`: `"인증"`
- `condition`: `"벤처기업 인증 보유"`, `"이노비즈 인증 보유"`
- `value`: **시스템 키 문자열** (단일) 또는 **시스템 키 배열** (복수) — 부록 2 매핑표 참고
- `operator`: `"보유"` (보유 필수) | `"미보유"` (없어야 함)

**사용자 표시 관점 보완**
- `condition`은 `"벤처기업"`처럼 인증명만 적지 말고, `"벤처기업 인증 보유"`처럼 조건 의미가 드러나게 작성
- 여러 인증 중 택일 (OR)이면 `condition`에 그대로 반영
  - 예: `"벤처기업 / 이노비즈 중 1개 이상 보유"`

> ⚠️ **OR 매칭 주의**: 현재 matcher (`backend/app/matcher/matcher.py:204-239`)는 복수 키를 **AND**로 처리. OR 매칭이 필요한 경우 v0.3에서는 `value: null` + `notes`에 원문 표기 + 운영자 토론 후 PR#6에서 matcher OR 지원 추가 검토.

**예시 (AND)**:
```json
{
  "field_name": "인증",
  "condition": "벤처기업 인증 보유",
  "value": "venture_company",
  "operator": "보유",
  "evidence": "벤처기업 인증을 보유한 중소기업"
}
```

**예시 (OR — v0.3에서는 임시 처리)**:
```json
{
  "field_name": "인증",
  "condition": "벤처기업 / 이노비즈 중 1개 이상 보유",
  "value": null,
  "operator": "보유",
  "notes": "OR 매칭 필요 — matcher는 AND만 지원. 원문: '벤처기업 인증 또는 이노비즈 인증 중 하나 보유'. matcher OR 지원 후 value=['venture_company', 'inno_biz']로 변경 예정"
```

## 5. 모호 케이스 (확정 — 2026-06-01)

> **대원칙: `fields[]`에는 표준 7종(업력/매출/지역/나이/종업원 수/업종/인증)만 넣는다.**
> 시스템·평가(measure.py)가 7종만 채점하므로, 7종 외 조건을 fields에 넣어도 점수에 반영 안 되고 경고만 남는다.
> 7종 외 **자격요건**은 `notes`에 기록(정보 보존), **메타정보**(지원금액/규모)는 제외.
> 보고서는 메트릭을 **"표준 7종 자격요건 추출 P/R"**로 명명하고, "7종 외 조건 보유 공고 X% (미지원)"를 한 줄 disclose한다.

| # | 케이스 | 확정 룰 |
|---|--------|---------|
| 1 | 자격요건 vs 메타정보 (ann_001 신용점수, ann_005 융자한도) | 7종 자격 → `fields[]` / **7종 외 자격(신용점수 등) → `notes`** / **메타정보(융자한도·지원금액·지원규모) → 제외** |
| 2 | OR / 복합 조건 (ann_019) | **단일 field 유지** (분리 X). `condition`에 "또는" 표기, `value`는 배열, `notes`에 "OR(택1)" 명시 |
| 3 | 트랙별 자격조건 (ann_010 OI/AX) | 트랙들의 7종 매핑 가능 조건만 `fields[]`. 매핑 불가하면 **`fields: []` + `notes`에 트랙 설명** (§6 모범사례 따름) |
| 4 | confidence 필드 | **선택 필드** (필수 아님). 라벨러가 불확실할 때만 사용. measure.py는 미사용 |
| 5 | operator 필수화 | **적용** — 모든 수치 필드(업력/매출/종업원/나이)에 `operator` 명시. 기존 GT도 재정리 (함준규) |
| 6 | 자회사/계열사/모기업 | **신청 주체(공고가 지칭하는 그 기업) 기준으로만 라벨.** 계열/모기업 관계는 `notes`에 기록 (시스템은 회사 1개 프로필만 다룸) |
| 7 | 지역 — 본사 vs 사업장 | **구분 없이 `operator="소재"`로 라벨** (본사/사업장 중 하나라도 해당 지역이면 충족으로 봄). 구분 필요한 특수 케이스만 `notes` |
| 8 | 비표준 자격요건 (국적/대표자 자격 등) | **`fields[]` 제외 + `notes` 기록** (1번 대원칙과 동일) |
| 9 | "창업 후 N년 이내" 디폴트 | **"이내" = "이하"** (경계 포함). `operator="이하"`, `value=N` (ann_014/015 v0.2 일관) |

**적용 결과 — 기존 GT 조정 대상**: ann_001(신용점수→notes), ann_005(융자한도 제거), ann_010(업종 confidence=low → `fields:[]`+notes).

## 6. fields: [] 허용 (v0.3 신규)

표준 7종 매핑 불가한 자격요건만 있는 공고는 `fields: []` 허용 (ann_011 모범 사례).

- 라벨러는 **무리하게 표준 7종에 매핑하지 말 것** — 부정확한 라벨이 평가 신뢰도를 깎음
- 필수: `notes`에 매핑 불가 사유 + 원문 자격요건 기록
- 평가 시 `fields: []`는 정답으로 처리. 시스템도 `fields: []` 출력해야 일치
- 적용 조건: 신청자격이 표준 7종 (업력/매출/지역/나이/종업원/업종/인증) **중 하나도 해당하지 않는 경우**

**예시 (ann_011)**:
```json
{
  "announcement_id": "ann_011",
  "title": "2026년도 「상생형 AX 선도모델」 주관기관(대기업 등) 모집",
  "fields": [],
  "exclusions": ["스마트제조혁신 지원사업에서 참여제한 중인 기업은 참여 불가"],
  "notes": "신청자격이 '대기업(계열사 포함), 중견기업 등 주관기관'으로 표준 7종 어디에도 매핑되지 않음. 중소기업은 자격 보유 기업과 컨소시엄으로만 참여 가능."
}
```

## 7. condition 작성 규칙

사용자에게 표시되는 값을 기준으로 작성한다. `condition`은 공고 원문을 그대로 복붙하는 문장이 아니라, **사용자가 화면에서 보고 바로 이해할 수 있는 형태**로 정리되어야 한다.

### 원문 그대로 vs 정규화

| 케이스 | 규칙 | 예시 |
|--------|------|------|
| 수치 조건 | 원문 의미를 유지하되 간결하게 작성 | `"3년 미만"`, `"2억원 이상"` |
| 지역명 | `REGION_GROUPS` 기준 정규화, 의미 분명한 형태 | `"서울특별시"` → `"서울"`, 필요시 `"서울 소재"` |
| 시·군·구 | 원문 그대로 사용 | `"광명시"`, `"춘천시"` |
| 복합 조건 | 원문 의미 유지, `/`로 구분 | `"10인 미만 / 5인 미만"` |
| 인증명 | 원문 그대로 쓰되 보유 여부가 드러나게 작성 | `"벤처기업 인증 보유"` |

### 사용자 표시 관점 보완 원칙

- `condition`만 보더라도 사용자가 조건 의미를 이해할 수 있어야 한다.
- 같은 유형의 조건은 공고마다 가능한 한 비슷한 방식으로 표현한다.
- 불필요하게 긴 설명문은 지양하고, 조건 중심 표현으로 정리한다.
- 단, 너무 축약해서 원문 의미가 달라지면 안 된다.

**예**:
- 나쁨: `"창업 후 7년 이내인 기업만 신청 가능"`
- 좋음: `"창업 후 7년 이내"`

- 나쁨: `"강원특별자치도에 본사 또는 사업장을 둔 기업"`
- 좋음: `"강원 소재"`

## 8. operator 후보 목록

| operator | 적용 필드 | 설명 |
|----------|-----------|------|
| `"미만"` | 업력, 매출, 종업원 수, 나이 | 미만 (경계값 미포함) |
| `"이하"` | 업력, 매출, 종업원 수, 나이 | 이하 (경계값 포함) |
| `"이상"` | 업력, 매출, 종업원 수, 나이 | 이상 (경계값 포함) |
| `"초과"` | 업력, 매출, 종업원 수, 나이 | 초과 (경계값 미포함) |
| `"범위"` | 업력, 매출, 종업원 수, 나이 | N 이상 M 이하/미만, value: `{"min", "max"}` |
| `"소재"` | 지역 | 특정 지역 소재 |
| `"무관"` | 지역 | 전국, 지역 제한 없음 |
| `"포함"` | 업종 | 허용 업종 목록 |
| `"제외"` | 업종 | 금지 업종 목록 |
| `"보유"` | 인증 | 인증 보유 필수 |
| `"미보유"` | 인증 | 인증 없어야 함 |

> ⚠️ `operator`는 내부 비교용이지만, 실제 사용자 화면 표현과 논리적으로 일치해야 한다.
> 예: `condition = "7년 이하"`인데 `operator = "미만"`이면 사용자에게 잘못된 정보로 보일 수 있으므로 검수 시 반드시 확인.

## 9. confidence / notes 사용 기준

현재 `ground_truth.json` 스키마에 `confidence` 필드는 비공식 (ann_010 일부 사용). 정식 도입 여부는 §5 모호 케이스 §5-4에서 합의 예정.

**사용자 화면에 표시했을 때 의미가 모호해질 수 있는 조건**은 반드시 `notes`에 근거를 남긴다.

### notes에 기재해야 할 케이스

- 조건이 본문이 아닌 첨부파일·별표에만 있는 경우
- `"창업 후 N년"` 표현이 `"미만"`인지 `"이하"`인지 불명확한 경우
- 업종 조건이 포함/제외 목록이 혼재된 경우
- 수치 조건의 기준일(공고일/접수일/신청일)이 불명확한 경우
- 복수 조건이 AND인지 OR인지 불명확한 경우
- 지역 조건이 단순 지역명인지, 소재지 기준인지 사용자가 오해할 수 있는 경우
- 연령 조건에서 `"만 나이"` 여부가 불명확한 경우
- **표준 7종 외 자격요건을 표준 필드로 매핑한 경우** (매핑 근거 기록)
- **표준 7종으로 매핑 불가한 자격요건이 있는 경우** (원문 조건 + 매핑 불가 사유 기록)
- **범위(operator: "범위")의 inclusive 변환을 한 경우** (v0.3 신규 — 원문 `"미만"`을 `max: N-1`로 변환했음을 명시)
- **OR 인증 매칭 케이스** (v0.3 신규 — value: null + 원문 표기 + PR#6 matcher 보강 대기)

## 10. exclusions 작성 규칙

- 원문 의미를 유지하되, **사용자가 읽었을 때 바로 제외 사유를 이해할 수 있도록** 작성한다.
- 한 문장에 여러 조건을 과하게 묶지 말고, 가능한 한 항목별로 분리한다.
- 일반적인 공통 제외 조건 (체납, 휴폐업, 채무불이행)은 반드시 포함
- 업종 제외 조건이 있으면 별도 항목으로 분리

### 작성 원칙

- 원문 그대로 기재를 기본으로 하되, 화면 가독성을 해치지 않는 범위에서 정리 가능
- `[cite: N]` 출처 표기는 선택사항 (ann_001 스타일)
- 사용자가 "나는 제외 대상인지"를 빠르게 판단할 수 있어야 함

## 11. 라벨링 체크리스트 (v0.2 + v0.3 통합)

### v0.2 기존 체크리스트

- [ ] `title`이 공고 원문 제목과 일치하는가
- [ ] `source_url`이 실제 접근 가능한 URL인가
- [ ] `fields`에 표준 7종 외 필드명이 사용되지 않았는가

- [ ] 메타 정보(사업기간/신청방법/지원한도/제출서류 등)가 `fields`에서 완전히 제외되었는가
- [ ] 모든 수치 조건에 `operator`가 명확히 매핑되는가
- [ ] `"미만"` / `"이하"`, `"이상"` / `"초과"` 혼동 없는가
- [ ] 지역명이 `REGION_GROUPS` 기준으로 정규화되었는가
- [ ] `condition`만 봐도 사용자가 의미를 이해할 수 있는가
- [ ] 같은 유형의 조건이 다른 공고에서도 비슷한 방식으로 표현되었는가
- [ ] `exclusions`에 휴폐업/체납/채무불이행 포함되었는가
- [ ] `exclusions`가 한 문장씩 읽기 쉽게 정리되었는가
- [ ] 모호한 조건 또는 매핑 불가 조건은 `notes`에 근거가 기재되었는가
- [ ] JSON 문법 오류 없는가 (`python -m json.tool`로 검증)

### v0.3 추가 체크리스트

- [ ] 모든 수치 필드(업력/매출/나이/종업원)에 `value`(숫자) + `operator` 명시되었는가
- [ ] 매출의 `value`는 **원 단위 정수** (예: `200000000`)인가 — 부록 3 참고
- [ ] 범위 operator는 `value: {"min": N, "max": M}` 형식인가
- [ ] 지역의 `value`는 **배열** 형식 (`["원주"]`)인가
- [ ] 업종의 `value`는 **배열** + `operator`가 `"포함"` 또는 `"제외"`인가
- [ ] 인증의 `value`는 매핑표(부록 2)의 시스템 키 형식인가
- [ ] 매핑표에 없는 인증은 `notes`에 원문 표기 + `value: null` 처리했는가
- [ ] OR 인증은 `notes`에 원문 + `value: null` 처리했는가 (현 matcher는 AND만 지원)

| `ip_protection` | 특허, 지식재산권, 실용신안 |

**룰**:
- GT `cert_keys`/`value`는 위 표준 키만 사용.
- 표에 **없는** 인증/지정(조달청 혁신제품 등록, 중기부 R&D 이력, TIPS 선정 등)은 표준 인증이 아니므로 `fields` 제외 + `notes`에 원문 기록 (§2). cert_mapping 추가가 필요하면 함준규에게 요청 → 모듈과 본 표 동시 갱신.

> ⚠️ **시스템 정합 미완**: 현재 회사 데이터(`seed_companies.py`)와 매칭(`matcher.py`의 `match_certification`)은 구 키(`vc_certified` 등)를 사용한다. cert_mapping.py(PR#24) 표준 키로의 통일은 **별도 시스템 작업**으로 남아 있음. 평가는 cert_mapping 키 기준이므로 GT는 위 표준 키로 작성한다.

> 💡 **OR 매칭**: 복수 인증 택1(OR)은 matcher가 AND로 처리하므로 `value: null` + `notes`에 원문 표기.
